# 登记时自动采集与附加日志

用户要求「记个 Bug」「登记问题」或给已有 Bug 补日志时读取本页。登记默认分别判断 Web、Computer 与 Server 日志的必要性；需要的来源已有权限且目标明确时直接采集、保存并上传，无需再让 QA 手动寻找文件。判断无需采集时保存依据与已有证据；不因三类来源都要检查而强制读取或召回。Computer 来源按实际写入链路选择，可包含 desktopd、Companion、runtime-host 和相关执行诊断，清单沿用 desktopd 名称。工具仍由执行该 Skill 的 Codex 会话调用；本规则不创建常驻采集服务。

### 登记阶段的 Web 采集判断

- 涉及 Web 的上报，先发现已授权宿主的相关页面与原生日志能力，再决定采集或复用证据。截图能描述现象，不代表已保存页面身份、版本线索和触发时序；不得仅凭「只登记」「截图已足够」将 Web 标为 `not_needed` 或 `not_collected`。用户明确要求不读取日志时遵循其范围，并记录该限制。
- `supplementary`／「可辅助」表示日志有辅助证据用途，不表示可以直接跳过采集。存在现场关联或时序缺口、目标已匹配且只读入口可访问时，本轮按固定窗口流程读取并上传；无需等待开始代码分析，也不等待 QA 再问「Web 日志呢」。已有同目标、同窗口且覆盖充分的日志可复用，避免重复采集。
- 弹窗位置、mention、焦点、滚动等问题，日志不包含 DOMRect 或不能单独证明根因，不构成跳过现场日志检查的理由。先核对实际日志契约，保存能关联现场的保留记录，并在授权范围内补充必要的可见 DOM；明确当前观察与历史点击状态的区别。
- 结束登记前，Web 必须有真实的读取／复用结果、已尝试的具体阻塞，或基于已有充分证据的无需追加依据。未发现能力、未执行读取且没有替代证据时，不得把「可辅助」写成采集完成。日志空结果、覆盖不足和读取失败分别按下文状态记录；成功读取的附件须回读确认，失败或用户限制须在反馈中如实说明。

### 登记阶段的 Server 采集判断

涉及服务端请求、权限、成员关系、持久化或目录投影时，按 [服务端日志](server-logs.md) 检查实际 Tutti CLI 与已核实的 AWS 来源。判断 `required`或`supplementary`（必需／建议补／可辅助）后，本轮立即采集、保存并上传同一条Bug，不等待QA再问。先保存易失证据再深入代码分析；成功请求不得只查HTTP失败归因。认证过期主动发起恢复，有真实权限/目标缺口才提出必要问题。结束登记前Server须有实际读取/复用结果、具体尝试与阻塞，或充分的无需追加依据。

## 1. 确认目标与入口

读取数据目录配置与已有 Bug 档案。新记录先解析固定表格链接并读取当前字段；已有记录用真实 `record_id` 读取最新内容。沿用此前保存的创建结果，不因补附件重新创建 Bug。

从描述、截图、附件、已有日志和 QA 回复确认页面／Account、发生时间与时区、环境及版本。按 [Computer 定位与 QA 询问](computer-target.md) 判断 desktopd 日志用途并查询真实候选，核对本地或远端。目标仍不明确时暂缓该来源，先完成可进行的代码与证据分析，再按 [QA 反馈规则](qa-dialogue.md) 判断是否需要设备选择。登记本身不需要全部字段齐备，采集必须关联实际目标。

尽早获取已有权限内的易失日志，随后再做代码分析。先保留历史现场；采集不通过刷新页面、重启 Computer 或重新登录来制造替代日志。

判断需要 Web 日志时，本轮直接执行 [截图与 WebMCP 自动采集](web-logs.md#截图与-webmcp-自动采集必须执行)：结合截图定位页面，按 [固定流程](web-logs.md#固定流程提问前-10-分钟--单个-log-附件) 固定提出本次问题的时间，取得此前 10 分钟目标页面／Account 的全部保留级别记录；逐条取得的记录归并为 `web-logs.log`，已有诊断文件或包按下方原件规则上传到同一条 Bug 并回读，必要时补读可见 DOM。取得日志后核对它是否补齐因果节点；仍有缺口时按 [业务推演](root-cause-analysis.md#2-用缺失的因果节点驱动补采) 继续验证其他边界。不等待 QA 再次询问或重复确认已有授权；真实目标、权限或原现场材料缺口另存尝试与恢复条件。

判断 Server 必需或建议补时，本轮直接执行 [服务端采集](server-logs.md)，沿用最初窗口，通过实际Tutti CLI或已确认AWS日志来源补齐并附到同一条Bug。

## 2. 自动采集相关来源

| 来源 | 获取方式 | 必须保存的关联信息 |
|---|---|---|
| Server | 按 [服务端日志](server-logs.md) 调用实际Tutti CLI，覆盖不足且AWS来源已核实时用AWS CLI补采 | 服务/环境、CLI/API origin或AWS账号/profile/区域/日志组、账号/房间/会话/request/trace关联、查询和实际范围、分页/截断、成功/失败类别、版本及限制 |
| Web | 按 [WebMCP 获取步骤](web-logs.md#获取步骤) 识别截图页面，使用已授权且实际支持原生工具的桥调用 `get_web_logs`；已有诊断导出附件则读取、筛选 | 页面与 Account 关联依据、工具参数、返回的页面 ID、时间范围、记录数、截断信息与版本 |
| 本地 desktopd | 目标已确认是执行主机时，按 [本地日志读取](computer-logs.md#本地读取指定文件) 解析配置中明确的 desktopd 文件，筛选时间与定位标识并保留相邻状态／堆栈 | 目标确认来源、实际文件、选择条件、实际覆盖时间、未知时间戳和轮转缺口 |
| 远端 desktopd | 按 [远端召回](computer-logs.md#远端复用-tutti-日志召回) 与 [tutti-ops CLI](tutti-ops-computer-logs.md) 复用或创建目标日志召回，下载、校验、读取包，再提取相关 desktopd 片段 | 环境、computerId、taskId、请求与实际时间范围、包校验结果、文件清单与截断信息 |

Web 的 range、limit 与返回预算遵循原工具契约；固定流程省略 level、显式 limit 200，查询覆盖提问前 10 分钟的范围后在本地截取，接口不支持的历史起止时间不作为查询参数。截断时分级补查并合并；仍不足时保存缺口及历史导出恢复条件。desktopd 按发生时间、请求／会话／安装任务标识筛选，保留必要的 info 与状态事件，不只截取 error。时间未知时先核对现有证据，保存待核对项并继续独立分析；需要追问时按 QA 反馈规则执行。当前日志注明真实范围，不能声称覆盖历史故障。

桥、远端 CLI/MCP、权限或目标资料不足时，记录具体缺口及恢复方式，继续取得不受影响的来源。成功返回空结果与调用失败分别记录。只有代码链路与现场证据均支持某来源不参与该问题时，才记 `not_applicable` 并写明依据。

## 保存证据与采集结果

每轮在 Bug 的 `evidence/registration-<run-id>/` 保存取得的原始材料、查询回执、采集清单和必要分析。保留此前证据，新运行使用新目录；附件选择遵循下方规则，本地文件不意味着逐项上传。清单形状见 [登记日志清单模板](../assets/registration-logs.json)。Computer 清单沿用 `desktopd` 来源键，实际组件与上传文件在 `artifacts` 记录。

### 日志文件与附件数量

按 Web、Computer、Server 三类来源集中提交日志，只上传实际取得的相关来源，不为凑齐三类制造空文件。原截图、人工附件与历史证据保留；补采先查当前附件和上传回执，复用同目标、同窗口且充分的材料，相同 SHA-256 的文件只上传一次。

| 取得形式 | 保存与上传 |
|---|---|
| 工具／QA 已提供或本地已确认并取得单个／多个日志文件、诊断 ZIP、召回包 | 读取并核对目标、内容与覆盖后原样上传，保留文件名、内容及结构；多个原文件可一起提交，包无需拆成组件附件，也无需再上传合并件或摘录。清单记录包内文件和相关事件位置，原件的数量不受三份汇总件约束 |
| WebMCP、CLI、API 或远端只读入口逐条返回内容，尚无可直接上传的日志文件 | 同类来源各生成一个 UTF-8 汇总件：`web-logs.log`、`computer-logs.log`、`server-logs.log`。分页、分级补查、多个组件／轮转片段与同轮补采全部归并到对应来源，再上传完整汇总件；不按查询、时间片、组件或假设创建附件 |

把逐条返回写成多个临时 JSON 不改变取得形式，仍须按来源合并；实际取得的日志文件／包走原件分支，能直接取得原文件时不以内容摘录代替原件。

复制 MCP 连接链接取得的 Web 日志按用户要求保留未脱敏内容，记录 `redacted: false`，不再移除日志字段；仍须核对目标页面／Account，连接链接的片段凭证不得写入附件。其他来源沿用既有处理规则。

沿用已有凭证与非目标私密数据处理规则。需要脱敏时保留原件本地，上传注明脱敏范围的副本，记录与原件的对应关系；其余原文件不为压缩数量而筛选、拆分或改写。已取得原文件但后续分析产生了摘录，只上传原文件，不同时附摘录。

**逐条内容的合并规则**：

- 保留故障前置状态、触发、异常和后续恢复／成功的完整必要上下文；Web 固定窗口内全部取得的保留记录仍全部纳入。各来源元信息包括目标、环境、查询参数、请求／实际覆盖、时区、截断、采集状态及原始来源。
- 按事件发生时间升序合并，保留原始时间和时区；排序可换算 UTC，但不得用采集时间代替发生时间。同时间记录稳定保留来源与原顺序，跨进程时钟偏差另记限制，不能仅靠排序推断因果。
- 每条记录保留来源组件／文件／查询、原行号或序号、原始内容和关联标识。堆栈及多行事件作为一个整体随所属事件排序；无法归属的无时间记录单独标记并保留原顺序，不编造时间。
- 重叠查询仅按同来源、同事件 ID 或完整记录及发生时间去重，保留重复聚合的首次／末次和次数，不因事件名相同删除真实重复执行。格式为 JSON Lines 时使用 metadata 首行和完整记录后续行，检查可解析及实际覆盖；普通文本也需保留多行事件边界和来源信息。

保存最终文件 SHA-256、文件／包来源、真实覆盖、脱敏记录、file token 与回读结果。原始分页 JSON、工具发现文件、失败回执、采集 `manifest.json`、截图水印／DOM 中间结果、分析报告及测试输出默认留在本地档案，其必要结论写对应字段，不另列日志附件。只有用户明确要求交付这些材料或独立验收确需时才上传，避免逐轮重复报告、清单和测试文件。

补采产生新内容时先归并，提交本轮每来源的完整日志或新增原文件，并在「相关日志」注明有效文件及覆盖关系；不重复提交已有原件或把每次补查分成附件。不支持安全替换时保留旧附件，旧版清理仅在明确授权后执行。

Web、Computer、Server各记录一个结果：

每个来源同时保存 `necessity`（`required`／`supplementary`／`not_needed`／`undetermined`）、`rationale`（假设、缺失观察或无需采集的依据）、`expected_evidence`（目标、状态或事件）与 `next_action`。这是本轮证据需求判断，独立于采集 `status`；已有档案未包含这些字段时本轮补齐。无需追加时引用已经取得的证据；未采集不等同于取得空日志。

| status | 含义 |
|---|---|
| `captured` | 成功读取与目标关联的日志，覆盖所需范围 |
| `empty` | 成功查询目标与范围，实际结果为空；保留返回结果／覆盖依据 |
| `partial` | 已取得片段，但存在截断、轮转、时间或版本覆盖缺口 |
| `blocked` | 无法采集；保存失败类型、缺少条件、提供方与恢复方式 |
| `not_applicable` | 有证据确认该来源不参与问题，保存依据 |
| `not_collected` | 当前无需采集但来源仍可能相关；保存充分的替代证据与判断依据，不能用于掩盖必要采集受阻 |

模板的 `pending` 只用于尚未检查的来源；登记结束时三类来源均须有结果。采集状态与上传状态分别记录，文件已保存在本地不等于已上传飞书。

## 4. 写入同一条 Bug

1. 按真实字段与 CellValue 契约创建 Bug，或用已保存的 `record_id` 更新同一条记录。标题、描述和原始截图照常登记，阶段为 `bug单`；采集失败也保留记录与缺口。创建结果未知时先查结果再恢复，避免重复建单。
2. 按 [日志文件与附件数量](#日志文件与附件数量) 仅将实际原文件／包或各来源的最终汇总日志用专用命令追加到 `field_map.attachments`，采集清单不作为默认附件。CLI 参数以当前 `--help` 为准；使用 `lark-cli base +record-upload-attachment` 时，以证据目录为工作目录传入相对路径。`empty` 在日志元信息和字段中记录真实空结果，读取失败只记阻塞与回执，不上传伪造日志。
3. 重新读取 `field_map.logs`，保留已有人工内容，追加本轮 `【登记日志：<run-id>】` 摘要：来源、结果、目标、时间范围、附件文件名、实际上传结果及剩余缺口。精简关键日志可放在这里，完整必要片段放附件；缺少来源时也写明缺口。
4. 保存附件上传返回的 file token、记录链接、返回值与最终文件摘要，重新读取 Bug 确认实际原文件／包或汇总日志的 token 存在。成功取得并上传的现场日志、只有能力发现／失败回执、采集受阻分别反馈，测试输出不能称为 Web 日志。重试先核对回执和最新附件，仅补传缺少的文件；上传失败保存本地产物和具体错误，后续恢复同一记录。

完成条件：记录写入确认成功、三类来源都有结果、可获取的必要日志已确认附到本条 Bug，日志摘要与上传回执已保存。采集和上传缺口写入技术记录；QA 回复按 [反馈规则](qa-dialogue.md) 组织，日志不足时继续可进行的分析。只有截图的记录不能描述为已携带完整日志。普通上报完成登记后继续根因分析；登记本身不证明根因、方案批准或修复验证完成。
