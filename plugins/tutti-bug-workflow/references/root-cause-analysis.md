# 业务逻辑、日志与复现路径

建立假设、验证证据和确认根因时读取本页。目标是解释本条 Bug 的业务现象如何形成；完成日志采集或解释某条报错，只完成了其中一个证据边界。

## 1. 从业务状态建立因果链

先写清 QA 的期望与实际表现，阅读入口、状态 owner、请求与结果消费者、相关测试及错误恢复分支。按真实业务流程画出正常路径，再对齐同次操作的日志：

`触发条件 → 输入／前置状态 → 执行或请求 → 首个错误状态 → 后续消费／恢复 → QA 可见现象`

在 `analysis.md` 逐节点记录期望值、实际值、代码位置、日志时间与关联标识，以及「现场事实／代码推断／待验证」。日志保留触发前的前置状态和错误后的重试、降级、成功响应、回执、状态更新；按同一用户、目标、请求／任务／操作标识关联，注明版本、时区与跨端时钟偏差。仅时间接近或错误文案相同不能建立因果关系。

每个因果连接都要说明上一状态通过哪个业务分支产生下一状态。尤其核对错误是否被捕获、是否有替代读路径、是否随后恢复，以及成功结果是否被消费者采用。最早的 error 日志不必是首个错误状态；对业务允许的暂缺、等待或重试，验证它是否被错误消费、恢复条件是否被破坏，或是否独立造成 QA 的异常表现。仅存在这类事件不能确认功能根因。

## 2. 用缺失的因果节点驱动补采

每取得一批证据，重新演算整条路径：日志是否支持该业务分支、后续恢复是否与假设冲突、最终表现是否能推出。发生矛盾时修订或排除假设，再取得能区分剩余原因的上下文。

| 仍缺的观察 | 下一项验证 |
|---|---|
| Web 只有请求失败，没有业务执行、写入或回执结果 | 沿请求／任务标识补 Server 日志；实际执行在 Computer 时再补对应 Computer 日志 |
| Server 已接受命令，但没有执行、发布或消费者状态 | 关联 Computer 执行与发布，再核对 Server 接收及 Web 消费；已有充分材料直接复用 |
| Computer 执行成功，但最终界面仍异常 | 查发布／接收结果、响应实际内容及 Web 状态更新；HTTP 200 本身不能证明返回了正确业务状态或界面已采用 |
| 某条错误随后恢复，但原假设仍把它当成永久故障 | 对齐恢复前后日志，检查后续状态；不能用被保留的历史错误请求或截图文件时间推断异常仍持续 |
| 现有日志契约未记录决定性的状态、响应或事件 | 先核对 producer 与可用入口，再做获授权的最小复现、断点、HAR 或隔离临时观测，记录历史现场仍无法补证的部分 |

采集按 [登记日志规则](registration-logs.md) 与各来源文档执行，并使用其集中附件规则。先自行取得已有权限内的上下文；一个来源受阻时继续其他可验证边界。所有来源都已读取仍不能推出结果时，保留具体缺口与下一动作，不能以日志数量充足代替分析。已有同目标、同窗口且充分的证据时无需机械补齐三端。

## 3. 推演并验证主复现路径

在给出根因前，从初始业务状态重新推演一条能产生原现象的路径，记录：

- 环境、版本、账号／目标、初始业务状态及必要时序；哪些已由现场确认，哪些为诊断控制条件。
- 用户操作、请求与异步事件顺序；每一步的预期状态、异常状态、日志／代码依据及下一消费者。
- 达到原现象的观察断言，例如最终仍保留运行中状态；只复现中间 409 或内部异常不能代替原现象。
- 实际使用的测试、命令或操作、结果及证据位置；逻辑推演与已执行复现分别标明。不能安全执行的步骤注明原因及可替代观察。

检查必要触发条件：去掉该条件后，同一路径是否回到正确业务结果；安全可行时运行正常对照或控制时序验证。测试替身只控制外部返回或时序，核心业务与恢复决策使用真实 owner。复现只在本轮 main 成立而现场版本／日志无法关联时，结论限于代码机制，现场根因继续标为未确认。

## 4. 再检查其他复现路径

主路径形成后，阅读同一状态 owner 的其他入口和消费者，按已发现的业务边界检查不同操作顺序、重复操作、并发、恢复／重试、跨页面恢复、重新打开或不同响应先后等相关路径。只选择可能进入同一错误状态的分支，不扩展无关功能。

对每条路径写出共享的错误状态、不同前置条件、如何到达同一现象，以及实际验证结果。区分「已复现／仅推演／已排除／受阻」，引用日志或代码依据；尚未执行的候选不能纳入已确认影响范围。未发现其他路径时，写明检查过哪些入口与分支、为什么不能到达该错误状态，而不是简单写「无」。

## 5. 确认根因的完成条件

只有业务链、现场证据与主路径验证能共同解释原现象，才可标记已确认：触发条件明确，首个错误状态已定位，每个关键传播／恢复节点均由现场上下文或实际测试／复现支持，主路径能推出原表现，相关竞争假设与反例已处理，其他可达路径已检查并区分确认程度。已有完整现场轨迹可验证关键因果时，不强制重复有风险的生产操作；实际执行与日志重建分别记录。

缺少关键节点时保存「原因未确认」、已证实的机制、仍成立的假设、缺失观察及下一项采集／验证动作。只有影响验证且由 QA 独占的现场信息才按 [QA 反馈规则](qa-dialogue.md) 提问；结束前继续本轮可自行完成的关键验证。
