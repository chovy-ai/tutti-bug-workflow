# 服务端日志：判断后立即采集

登记或分析涉及控制面请求、权限、成员关系、持久化或状态投影时读取本页。目标是在日志轮转、过期或现场变化前保存证据。仅登记也须检查；用户明确禁止读取时遵循限制。

## 判断与执行

每轮记录 Server 是否参与、`necessity`、候选原因、已有替代证据与缺失观察。`required`（必需）和 `supplementary`（建议补／可辅助）都要求本轮立即执行采集或复用同目标、同窗口且覆盖充分的材料，不能以“建议补 server 日志”结束，也不等待 QA 追问或重新批准已有权限内的读取。代码能解释现象，但成功请求、写入结果或现场版本未关联时，不能据此跳过。

登记开始先判断易失证据并采集，随后再深入读代码；分析中发现新缺口时立即补采。无需追加必须引用充分的替代证据；来源不参与才标 `not_applicable`。无法采集记录真实失败和恢复条件，不能把缺口改写成无需采集。

## 选择真实入口

1. 发现现有 Tutti CLI：按本机 `--help` 与 `schema` 确认命令名、只读性质、身份、API origin、支持的时间格式、筛选、分页和日志类别。当前插件默认入口是 `tutti-ops`；用户所称 `tutti-cli` 若是另一实际入口，读取其契约后使用，不猜命令，不因二进制名称不同停在建议。
2. 已有 Tutti CLI 支持所需日志时优先直接查询/导出。不能把安装成功、Token有效、目录查询或导出任务已创建当作取得日志；实际获取文件/记录后检查内容。
3. 核对日志类别。当前 `tutti-ops diagnostics http query/events` 是 HTTP **失败**归因入口；`HTTP_STATUS_CLASS_ALL` 表示 4xx/5xx，不代表包括成功请求。需要验证成功 join/写入时，失败查询为空不能排除操作；改走支持成功访问记录的入口。导出操作若被标为 write，检查实际副作用与任务授权，不静默加确认参数。
4. 已核实相关日志存储在 AWS，且 Tutti 入口缺少所需类别、上下文或历史覆盖时，按 [AWS CLI](aws-cli.md) 查询原始日志。复用既有账号/profile、区域和身份，先验证目标；配置字段为空不能代替能力发现。不要用其他账号或环境绕过权限。CLI失败和AWS补采分别留回执。
5. 认证过期时立即发起适用登录恢复并展示真实入口；必须本人登录/MFA、目标仍无法消歧或缺少新增权限时说明具体阻塞。继续不依赖它的工作，恢复后重试原窗口。不要要求 QA 手动寻找可由工具取得的日志。

## 固定范围与证据检查

- 沿用本次问题最初保存的 `question_time` 与提问前10分钟窗口，后续“日志呢”不重置它；可信发生时间或 Web 事件可帮助缩小、关联或追加窗口，但注明用途。无可信消息时间时记录接收近似时间及限制。
- 先确认服务、环境、账号/区域、日志组/索引，再以房间、会话、request/trace、route与时间限定查询。优先含成功/失败和必要正常状态事件；不只查 error。不要假定 userId、roomId、URL、响应体、DB提交或部署SHA一定被日志记录。
- 快速成功访问记录可能仅有 route模板、结果、状态、耗时和request/trace，没有具体路径、用户或请求参数。先核对 producer契约；按实际可用字段查询，不叠加不存在的字段造成假空结果。route模板搜索结果需用请求标识或其他证据关联目标，不能将同route的其他用户请求当成现场。
- 按实际契约分页至结束；有限预算/时间分片必须记录未完成部分。CloudWatch Insights轮询至终态，`Running`或聚合摘要不算完整证据；达到结果上限时继续合理分片或明确 `partial`。保留查询起止、实际记录首末时间、条数、截断、保留和聚合限制。
- HTTP 2xx只证明该请求成功返回，不证明每条DB写入均有审计。核对业务分支（例如 `alreadyMember`）、事务实现、可用持久化证据和版本，分别表述代码推断与现场事实。日志缺少关键字段继续保留待核实项。

## 保存、上传与结束条件

遵循 [登记日志规则](registration-logs.md#保存证据与采集结果)，在本轮 evidence 保存 `server-logs.log`（UTF-8，metadata与实际取得记录）及 `manifest.json`。原始查询/错误另存证据；未成功读取不伪造日志文件。脱敏凭证、Cookie、Token及非目标数据，保留必要诊断上下文。保存SHA-256、真实CLI/API origin或AWS profile/区域/日志组、参数、实际覆盖、结果、限制与恢复动作。

自动追加上传到**同一条**Bug的附件，保留原截图/Web/Computer材料，保存file token并回读确认。向“相关日志”追加范围/结果/附件摘要；分析发现写“排查验证”，未确认项或权限失败写“待核实与阻塞”。采集状态与上传状态分开记录，失败、空结果、覆盖不足不得混为成功。

结束前：`required/supplementary`已实际尝试读取并上传所有可取得的必要材料，或已有具体阻塞证据及恢复条件；不能仅完成建议。反馈已采集/部分/受阻的真实结果，不承诺所有来源均有日志。全流程只作用于本条Bug，不创建常驻监听或更改日志保留策略。
