# 工作流与交接

## 三个场景

`investigate` 面向 QA，交付证据充分的根因；`solution` 面向 RD，交付经讨论和批准的方案；`execute` 根据批准版本修复并验证。手动模式由用户在 Codex 中选择场景；后续流程服务按状态调度相同的 Skills。

每次进入场景读取同一 Bug 档案，核对 Bug ID、来源和最新输入。材料矛盾或版本变化时先更新分析或方案，保持交接可追溯。等待人回复时写清问题和当前状态，结束本次运行；回复到达后读取最新档案继续。

## 档案

使用 `scripts/dossier.py new-bug --bug-id ID` 创建数据目录下 `bugs/ID/`：

- `bug.json`：结构化状态、代码版本、QA 材料版本、根因与方案版本。
- `analysis.md`：根因证据、假设验证、未知项与 QA 提问。
- `plan.md`：根本方案、兼容方案、选择结果、设计图和修改范围。
- `acceptance.md`：期望行为、复现步骤、环境、版本核对方式、回归与验收标准。
- `verification.md`：执行结果、环境版本、证据引用、未覆盖场景。
- `dialogue.jsonl`：QA/RD 对话事件及来源引用。
- `evidence/`：最小必要证据。保存日志时记录环境、时间范围、请求标识、部署版本和采集方式。

新 Bug 登记与已有 Bug 补日志按 [登记日志规则](registration-logs.md) 自动检查并附上相关 Web、desktopd、Server 日志；逐轮证据、采集清单和上传回执保存在 `evidence/`。日志缺口随单记录，补采沿用同一 record_id。Server判断必需或建议补/可辅助后按 服务端日志 本轮立即调用Tutti CLI或已核实来源的AWS CLI，不等待QA追问。

普通 QA 上报登记后默认继续分析；明确仅登记或仅补附件、不分析时按其范围执行。面向 QA 的反馈与维护侧技术阻塞按「QA 只回答现场问题、技术缺口交给维护方」的原则分流，问题在本轮可自行完成的分析后提出，并关联具体假设与下一项验证。

`approval.json` 仅在收到真实 RD 批准后导入或根据已核实的直接消息记录；代理不通过自己生成的批准来授权自己。记录 Bug ID、根因/方案/验收版本、全部仓库基线、三份报告的 SHA-256、RD 身份、批准时间和原始批准引用。形状见 [批准记录模板](../assets/approval.example.json)。用 `scripts/dossier.py artifact-hashes --bug-id ID` 获取已展示给 RD 的三份报告摘要。

每次更新 QA 材料增加 `input_revision`；根因、方案或验收标准发生实质变化时增加对应版本，并重新核实依赖产物。把上次同意复用于变化后的方案需要 RD 重新批准。

开始修改业务代码前运行 `check-execution`，并通过原始消息或可信服务核实 RD 身份、批准原文和该方案版本。脚本检查本地一致性，不能单独证明消息来源或用户身份，也不能替代工具权限与可信审批服务。

## 状态

| 状态 | 含义 / 后续动作 |
|---|---|
| `pending_analysis` | 待分析 |
| `analyzing` | 验证根因假设 |
| `waiting_qa` | 已保存明确的补充资料问题，等待 QA |
| `pending_solution` | 根因已确认，可以设计方案 |
| `discussing_solution` | 与 RD 修订方案 |
| `waiting_rd_approval` | 方案和验收版本已明确，等待批准 |
| `fixing` | 执行已批准版本 |
| `verifying` | 核对部署版本并执行验收 |
| `waiting_acceptance` | 自动验证结果已记录，等待 QA/RD 验收 |
| `accepted` | 有真实 QA/RD 验收通过记录 |
| `blocked` | 环境、依赖或访问条件阻塞，并有具体恢复条件 |
| `returned` | 验收退回，根据证据回到分析、方案或执行 |

`verification.status` 独立表示 `not_run`、`passed`、`failed` 或 `blocked`。自动验证通过只进入 `waiting_acceptance`，人工验收决定 `accepted`。

## 飞书的三个流程状态

固定使用配置中的「Bug 列表」、`workflow_status` 单选字段及三个过滤视图。表中阶段用于 QA/RD 查看进度；本地详细状态继续用于等待、执行和恢复。

| 表中阶段 | 进入条件与内部状态 |
|---|---|
| `bug单` | 新 Bug、分析、等待 QA；`pending_analysis`、`analyzing`、`waiting_qa`。等待编写方案时也暂留这里 |
| `待 review 方案` | 根因与当前方案、验收标准已成功回填，供 RD 评审；`discussing_solution`、`waiting_rd_approval`，以及已批准后的 `fixing`、`verifying` |
| `已自动修复并验证，待验收` | 已完成实际修复，配置环境的部署 SHA 与修复一致，必要验收/回归用例通过，验证报告和证据已成功回填；`waiting_acceptance` |

旧记录未填写阶段时由 bug单视图兼容显示，不批量推断或更改旧记录。新记录默认 bug单。RD 仅改变阶段不构成批准；执行仍核实真实批准来源和当前方案版本。创建 PR、测试通过或上传截图任一项都不能单独进入第三阶段。

阻塞或验证失败保留当前阶段并在报告中写清原因。新证据推翻根因时回到 bug单；修正方案且完成回填后回到待 review 方案。人工验收退回后按证据回到相应阶段。人工验收通过在档案和验收记录中明确保存，第三阶段本身不能证明已经人工验收；未定义额外的表中终态前不擅自新增选项。

## 代码和环境

分析开始时通过 固定代码缓存 增量同步两个仓库的 main，成功后从固定完整 SHA 创建 Bug 独立 worktree。多个仓库分别保存 SHA，已有工作区保留。QA 报告环境的版本也单独记录，与 main 不一致时核实差异对根因的影响。

执行在 `codex/<bug-summary>` 分支完成。修改基于批准的代码基线；代码漂移需要重新评估，影响根因、方案或范围时回到 RD。验证环境记录实际部署的修复 SHA；无法确认版本时将验证标为阻塞。

修复前复现与修复后验证使用同一组验收标准。证据包含操作、断言、结果和版本；截图作为补充。没有稳定的修复前复现时记录限制，不把未执行的检查写成通过。

## 飞书适配

真实表格及字段映射已保存在配置中。每次操作核对当前字段结构与最新记录，使用飞书 record_id 定位同一个 Bug；不能按标题匹配后写入。需要独立对话表或运行表时再按确定的结构扩展。

报告按 [字段职责与回填契约](report-fields.md) 拆分为「分析结论」「根因分析」「排查验证」「代码基线」「相关代码」「修复方案」「验收标准」「验证结果」「QA/RD沟通」「待核实与阻塞」。三个场景分别更新自己拥有的字段或条目，先读取最新内容并保留人工修改。根因字段只写简洁因果链，不拼入基线、路径、方案或沟通；完整报告保存为本地档案，附件遵循 [集中日志规则](registration-logs.md#日志文件与附件数量)。修复前排查与修复后验证分别写入排查验证和验证结果，不能混淆。相关 PR、体验环境链接和修复后截图证据使用现有字段。

QA/RD 对话优先写入指定表格的对话记录。写入范围来自用户任务或可信流程指令，只回填该 Bug 的已映射字段。邮件、群聊和私信发送需要另有授权。

每条回填应携带 Bug ID、场景、输入版本和运行 ID，确认写入成功再推进状态。没有映射或权限时保留本地待回填产物，报告尚未回填。失败重试先查询写入结果，避免重复对话或记录。

## 提 Bug 结束后的会话归档

`bug-investigate` 在用户授权的提 Bug 范围确认结束后，执行独立节点：确认结束 → 固定当前会话快照 → 按 provider 上传 → 核对并保存回执 → 最终反馈。完整分析完成并成功回填、明确限定的登记/补附件任务完成，或用户明确结束范围时，按 结束判断与 session 上传 保存结束依据后执行。处理中、等待 QA、暂时阻塞和回填失败保持节点待执行；后续方案、修复验证、纯 Setup 和 Skill 维护不自动触发。

核对宿主 provider、当前 session ID 与原日志身份，复用 tutti-ops 认证，将确认的 uploadId、结束依据和快照摘要记录到本地 `session-uploads.jsonl`。同一结束节点先恢复/去重，最终反馈及新增消息不触发递归补传。归档受阻单独保存状态与下一动作，保留业务结果。会话上下文进入管理端 Session 日志服务，不增加飞书现场日志附件。

## 后续自动调度契约

本版没有监听器。后续服务须处理：记录创建/修改事件去重、忽略 Agent 自身写回、同一 Bug 串行运行、不同 Bug 并行、持久化等待与恢复、工作机器离线、有限重试、失败可恢复、按真实身份检查批准。

事件至少携带来源、事件 ID、Bug ID、输入版本、变更类型、操作人和发生时间。服务读取当前状态再派发场景，不能仅凭一次字段更新就重复执行修复。
