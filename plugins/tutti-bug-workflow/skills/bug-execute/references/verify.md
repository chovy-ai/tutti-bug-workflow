# 部署后自验证

PPE 部署成功后，自己按方案里的验收要点逐条验证。涉及 UI 的改动必须截图，存在运行目录（`bug-fixes/<taskId>/`），回复 Task 时作为评论附件上传。

## 什么时候必须截图

满足任一条就算涉及 UI，每条验收用例都要截图：

- tutti 的 `apps/web`、Web 依赖的 UI 组件、样式、文案、图标有改动；
- 验收要点里有页面上的表现（显示、布局、弹窗、状态、提示文案）；
- Bug 本身是页面上看到的问题（Task 描述的是界面现象）。

只改 server 或 Computer、页面上没有可见变化时，用接口返回、日志或测试输出做证据，可以不截图；但验收要点里写了页面表现的用例照样要截。

## 浏览器：连接本机 Chrome

用插件注册的 `chrome-devtools` MCP（`--autoConnect`）连接本机正在运行的 Chrome，使用它已有的 tutti.sh 登录态。

1. `list_pages` 检查连接。连不上（Chrome 没开、没开启远程调试）→ 判失败：「本机 Chrome 未运行或未开启远程调试，无法自验证」。
2. `new_page` 打开预览链接 `https://tutti.sh/platform/?webBranch=<分支>`（Server 改动通过部署时的 `server_lane` 生效）。**只操作自己新开的标签页**，不切换、不刷新、不关闭用户的其他标签页；验证结束 `close_page` 关掉自己开的页。
3. 页面停在登录页 → 判失败：「本机 Chrome 未登录 tutti.sh」。
4. 确认加载的是预览版本：页面能看到预览标识或资源来自预览，拿不准时在验证结果里注明。

## 逐条验证

对验收要点里的每条用例：

1. 按步骤操作（`click`、`fill`、`press_key`、`wait_for`），需要的测试数据就地准备，不动真实用户数据。
2. 到达断言要检查的状态后，用 `take_screenshot`（`filePath` 指向运行目录）截图，命名：
   ```
   fix-<短 ID>-<用例编号>-<yyyymmddHHMM>.png
   ```
   一条用例需要多张时在编号后加字母：`fix-<短 ID>-1a-…`、`fix-<短 ID>-1b-…`。弹窗、提示等瞬时状态截在出现时。
3. 判断断言：看截图和页面内容（`take_snapshot`），必要时查 `list_console_messages` 有没有新的报错、`list_network_requests` 的接口返回。
4. 记录结果：`passed`／`failed`／`not_run`（附原因）。

可选的修复前对照：在生产环境（Task 里的页面链接）按同样步骤截一张 `before-<短 ID>-<用例编号>-<时间>.png`，复现不出来就不截。

## 记录

- 截图都存在运行目录，回复 Task 时全部用 `--file` 作为评论附件上传（见 SKILL.md 第 8 步）；「自验证」里每条用例写出对应的附件文件名，不写本机路径。同一次回复里文件名不能重复，按上面的命名规则就不会撞名。
- 涉及 UI 的修复，同时把关键截图的说明写进 PR 评论（`gh pr comment`），方便 Review。

## 判定

| 情况 | 结果 |
|---|---|
| 全部必需用例 passed，涉及 UI 的用例都有截图 | 回复 Task：已部署待验收 |
| 任一必需用例 failed | 判失败，回复里写明哪条用例、实际表现和截图 |
| 涉及 UI 但没能截图（Chrome 不可用、未登录、页面打不开） | 判失败，写明原因 |
| 依赖连接器授权，新泳道无法验证 | 判失败，写明需要人工预配 binding |
| 改了 tsh-websocket 但新泳道缺 ws 基础设施、ws 没部署上 | 判失败，写明需要人工先建 WebSocket V2 基础设施 |
