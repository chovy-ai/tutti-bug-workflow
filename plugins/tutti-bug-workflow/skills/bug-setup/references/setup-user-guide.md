# 使用者看得懂的准备流程

用于环境准备、登录失效或确实缺少权限时的引导。Agent 负责检查、准备与验证；你只完成必须由本人操作的登录或授权。正常 QA 上报中的技术缺口由环境维护方处理，QA 只补充必要的现场信息。

## 从检查到完成

1. **确定要准备什么**。例如“准备 QA 提 Bug 的环境”。Agent 按该场景选择工具，复用已经安装的工具和有效登录态。
2. **先完成安装**。Agent 检查本地环境，安装或复用本轮所有选中工具，并验证实际入口与版本。先处理可修复的安装错误；无法解决的项单独记录。此阶段不提前发起业务登录。
3. **安装结束立即进入授权**。无需你再次催促，Agent 检查已就绪工具的身份和权限，修复范围内的配置、发起登录或授权流程；需要本人操作时，给出已生成的链接、二维码或安全的本机认证入口，说明实际用途与权限范围。一次只提出当前需要的操作。
4. **由你登录或授权**。在真实网站、工具授权窗口或本机认证终端完成。密钥保存在认证存储中；对话只需要你回复“已完成”或说明遇到的提示。
5. **Agent 重新验证并继续**。你的回复表示可以复查，实际访问成功才算准备完成。仍然失败时说明本次具体原因与下一步；其他独立准备继续进行。
6. **交付简短结果**。说明哪些已可用、哪些等待你登录或授权、哪些需要维护人员接入，以及受影响的能力。已授权且可用的步骤直接复用。

本人操作或管理员权限确实必需时，相关步骤等待完成，Agent 继续独立准备；收到完成消息后接续原流程。用户明确只梳理、只安装或跳过授权时保留这一选择，否则主动处理当前所需的认证和权限缺口。

## 主动补齐授权

这是安装阶段结束后立即执行的授权流程。工具安装全部完成或分别确认阻塞后，Agent 自动进入本阶段；安装脚本与只读清单本身不承担交互式认证。

1. **检查**：先读实际工具帮助，复用已有配置和身份。分别检查命令可用、登录有效、权限范围、目标资源可访问。完整初始化检查飞书、GitHub 仓库、tutti-ops 与 Tutti CLI；指定场景仅检查必需项和选中的条件项。
2. **处理**：已有明确授权的配置修正、登录发起、只读复查直接执行。根据实际错误区分缺少凭证、凭证过期、scope 不足、资源 ACL、网络故障或入口未接入；每类采用对应恢复方法。必要输入优先从已有配置获取，仍未知时只询问当前需要的值。
3. **本人操作**：OAuth 同意、MFA、管理密钥签发及秘密输入在真实站点或安全的本机认证入口完成。Agent 可以打开正确页面、准备命令；Token 不进入聊天、命令参数、报告或插件源码。所需服务端授权由有权限的人批准，Setup 不自动授予自己角色或修改资源 ACL。
4. **恢复**：保存非秘密的步骤、目标环境、失败原因与恢复检查。用户回复“已完成/已授权”时先完成对应客户端登录，再验证身份和原目标访问；这句话本身不是验证结果。临时 device code 仅用于当前授权流程，若需跨轮保存，使用用户私有临时文件并在成功或过期后清理；授权链接过期则按原范围重新生成。
5. **完成**：实际成功才标记“已验证”。未完成时明确等待哪个本人操作、管理员处理或输入，以及下一次验证命令；不重复无变化的失败请求。至少推进到真实外部等待点，其他独立步骤继续。只读检查无法证明写入能力时，记录授予范围/ACL 证据并将实际写入留待首个已授权业务操作；不用试建 Bug、创建召回、推送或部署来测试权限。

| 入口 | 主动处理与恢复验证 |
|---|---|
| 飞书 user 登录或 scope 缺失 | 复用现有应用配置，用 `lark-cli auth status --json --verify` 检查用户身份；按工作流所需或实际 `missing_scopes` 发起 `auth login --scope … --no-wait --json`。有可用的 `lark-shared` Skill 时读取其认证规则，否则用 CLI 帮助确认参数。将返回 URL 原样展示，并用 `auth qrcode` 生成 PNG 放在链接后。此轮交还用户操作；下一轮由 Agent 用本流程的 `--device-code` 完成登录，再验证 user 身份与 Bug 表字段、视图和必要记录读取。保持 `--as user`。 |
| 飞书应用未配置或资源权限不足 | 应用配置缺失时按 CLI 实际引导准备；已有应用不重复创建。scope 和表格/附件 ACL 分别处理：提供实际授权/资源入口及最小所需范围，用户或管理员处理后重试原只读请求。记录创建/更新与附件上传权限分别核对。 |
| GitHub / 仓库 | 复用既有 Git 凭证与 gh 身份，分别只读验证三个仓库的 main。认证失效时按实际工具启动登录；组织 SSO 或仓库权限不足时给出真实失败提供的入口。保持用户指定账号；执行交付的推送/PR 权限另行核对。 |
| tutti-ops | 按 [环境与认证](tutti-ops-computer-logs.md#环境与认证) 对实际 origin 检查 `auth status`、`auth permissions`；缺少 Token 时打开下方管理密钥入口并准备 `configure-tutti-token` 的隐藏输入终端，直接验证并保存 Token。本人签发/配置后复查身份、Computer 与任务权限及设备目录；新召回写权限仅在该能力确需时申请。 |
| Web / 验收浏览器 / MCP | 先发现实际入口并尝试只读访问。已有桥但缺少站点允许或登录时，打开目标页面并引导本人完成可见授权，再调用目标工具验证。桥、服务器地址或验证环境缺失属于接入/输入问题，继续准备可自动完成部分并具体询问缺少的信息。 |

## 需要你操作时怎么说

使用“要完成什么 → 你需要做什么 → 完成后我做什么”的表达。下面只是对应情况的示例，实际入口、账号、设备和权限按当前证据填写。

| 当前缺口 | 给使用者的引导 |
|---|---|
| 飞书登录失效 | “为了读取和回填 Bug 表，需要你完成一次飞书登录。我会提供实际登录入口；完成后我会检查表格是否能访问。” |
| 飞书缺少表格权限 | “当前账号还不能更新这张 Bug 表。请让表格负责人为这个账号补充所需权限；完成后我会重新验证回填。” |
| 现场页面需要本人允许诊断 | “为了查看这次问题发生时的页面日志，请在当前 Tutti 页面完成诊断访问授权。完成后我会继续读取相关日志。” 只有实际出现站点允许操作时使用；浏览器桥缺失按维护接入处理。 |
| 缺少远端日志认证 | “要从远端设备读取日志，需要先在管理端准备访问密钥。请按下面的步骤在本机配置，完成后回复‘已完成’，我会检查设备和日志是否可读。” |
| 有只读密钥，需要新日志采集 | “已有权限可以查询历史日志。为了让这台设备上传新的故障日志，还需要‘Computer 与任务’的可写权限。请按下面的步骤准备具备该权限的密钥，完成后我会重新检查并继续。” |
| 仓库或浏览器工具尚未接入 | 说明受影响的能力和需要维护人员提供的接入；不把缺少工具误写成“请点授权”。 |

只依据真实失败提出补充权限。登录失效、缺少资源权限、工具未接入和网络问题分别判断；单个错误码不足以决定更换密钥。授权请求说明实际用途和所需范围，不把整份技术清单交给 QA。

## 远端日志如何授权

以下入口和表单名称已通过 Computer Use 在管理端核对。

1. 打开 [管理密钥页面](https://admin.tutti.sh/admin-tokens)，用有相应权限的管理端账号登录。也可以从左侧“全局 → 管理密钥”进入。
2. 点击 **新增密钥**，填写便于辨认的备注，例如 `tutti-bug-workflow`。
3. 点击 **详细控制模块权限**，按本次需要选择：

   | 要做的事情 | 整体权限 | Computer 与任务 |
   |---|---|---|
   | 查询设备、下载已有日志 | 只读 | 只读 |
   | 让设备采集并上传新的日志 | 可写 | 可写 |

   整体权限是上限；需要新日志时，两处都要允许写入。其余模块按团队要求关闭或保留只读。实际权限仍受创建者的管理员权限限制。
4. 选择有效期。当前表单默认 **90 天**，可按团队要求调整；点击 **创建**后立即复制完整 Token，完整内容只展示一次。
5. Agent 在安装结束后准备下面的本机命令，将 `PLUGIN_SOURCE` 换成实际插件目录。你只需在 `Tutti admin token (hidden):` 提示处粘贴 Token，输入内容不会显示：

   ```sh
   python3 PLUGIN_SOURCE/skills/bug-setup/scripts/workbench.py configure-tutti-token --admin-url https://admin.tutti.sh
   ```

   Setup 直接验证并保存到 tutti-ops 的本机配置，后续自动复用，无需另外登录。已有 Token 可通过宿主安全环境配合 `--token-env` 导入；Token 只进入本机秘密输入通道，不发送到聊天，也不填写到 Bug 表。
6. 回到对话回复 **“已完成”**。Agent 复查身份和本轮实际所需权限，再继续设备查询或日志获取。身份检查成功与创建新召回成功分别验证。

如果无法登录管理端或没有创建密钥的权限，请让有权限的环境维护人员完成这一步。Token 失效时，通过管理端重新准备并导入本机；已有可用 Token 时直接复用。技术验证命令见 [tutti-ops 环境与认证](tutti-ops-computer-logs.md#环境与认证)。
