# 报告字段与回填职责

飞书每条 Bug 使用独立字段保存各类信息。提 Bug 场景无状态，详细调查只存在于本次会话，飞书字段是唯一保留的结果，因此要写到他人能独立读懂；investigate 通过 `scripts/feishu.py write` 写入（覆盖或追加由脚本按字段控制，写后回读）；附件按 集中日志规则 提交，不逐轮上传报告、清单和测试输出。不得把所有内容重新拼进「根因分析」。字段通过配置中的真实 ID 定位，写入前读取当前字段结构与记录。

## 字段契约

| 配置键 | 飞书字段 | 内容 | 拥有场景 |
|---|---|---|---|
| `analysis_conclusion` | 分析结论 | 已确认事实、初步判断与确认程度；区分代码复现和现场确认 | investigate |
| `analysis_report` | 根因分析 | 触发条件、首个错误状态、因果链、影响范围；原则上两到四句 | investigate |
| `investigation_evidence` | 排查验证 | 修复前测试、日志、断点、主复现路径与其他可达路径、验证命令与实际结果；区分推演与已执行并引用证据 | investigate |
| `code_baselines` | 代码基线 | 各仓库 SHA、获取时间、工作区、现场版本与差异 | investigate；后续场景追加自己的执行/部署版本 |
| `code_references` | 相关代码 | 根因相关文件和行号，标明仓库与版本 | investigate；后续场景追加本次相关改动 |
| `solution_report` | 修复方案 | 根本方案、兼容方案、取舍、范围、方案版本与批准状态 | solution；investigate 仅写明确标为未评审的候选建议 |
| `acceptance_report` | 验收标准 | 复现条件、期望行为、验收断言、边界与必要回归 | solution |
| `verification_report` | 验证结果 | 修复后的实际检查、部署 SHA、结果、未执行/失败状态 | execute |
| `dialogue` | QA/RD沟通 | QA 澄清、现场追问、RD 决定和原始来源引用 | 各场景追加 |
| `open_items` | 待核实与阻塞 | 未验证假设、资料缺口、技术阻塞、影响与恢复条件 | 各场景维护自己的条目 |

`analysis_report` 保留原字段 ID，原显示名「原因分析」改为「根因分析」。该键只表示根因正文，不再是多场景报告的通用容器。

既有标题、描述、流程状态、日志、附件、PR、体验地址和修复后截图字段继续按原契约使用。「相关日志」描述实际采集范围和结果，不用诊断测试输出伪装现场日志。

## 写入步骤

1. 读取当前记录的输入、各目标字段、附件和 QA 回复；新输入或冲突按场景流程重新评估。
2. 按字段职责写简洁内容；版本与来源放在对应字段的简短条目中。
3. 只更新本场景拥有的字段或条目。共享字段保留其他场景和人工内容；没有新结果的字段不清空。首次分析可以将验证结果标记「未执行修复验证」，不能把修复前测试通过写成修复通过。
4. 候选方案不构成正式方案或批准。正式方案与验收由 solution 写入；execute 不把未经批准的建议转换成执行计划。
5. 写入后核对实际结果再推进流程阶段；字段缺失或写入失败保留待回填产物和技术缺口，不能退回把全部报告塞进根因字段。

## 旧记录兼容与迁移

旧记录可能仍在原字段中保存分节报告。读取时识别根因、方案、验收、验证和沟通分节；在迁移完成前保留其人工内容，不因改显示名丢弃旧报告。只迁移用户指定的记录，不根据新规则批量覆盖历史数据。

迁移前保存原始记录或报告附件，再按明确分节迁到目标字段。目标字段已有内容时先合并并处理冲突；未知分节保留在原始备份，报告待人工核对，不能静默丢弃。新字段写入成功后，再把原字段收敛到根因正文。阶段、原图、日志和人工批准来源保持不变；记录布局变化不提高根因确认程度，也不增加方案/验收批准版本。

## 配置迁移

共享数据目录的 config.json 与分发默认配置都使用上述 field_map。只补充本表实际验证过的字段 ID，保留仓库、日志路径、认证、其他表格和个人配置；更换 Base/Table 时重新解析全部字段。init 对已有配置保持幂等，不自动覆盖。setup 对旧配置读取实际字段后补齐映射，缺权限时保存准确的恢复条件。
