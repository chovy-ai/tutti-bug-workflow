# QA 反馈、追问与恢复

准备回复 QA、决定是否追问或收到补充时读取本页。普通上报先自行完成本轮可进行的分析，再反馈结论或必要的现场问题。

## 追问前的完成条件

先使用最新记录、截图／录屏、历史问答、可访问日志与目录，阅读相关代码和测试并验证候选原因。未确认的设备或时间暂记待核对，先完成其他不依赖它们的分析；只有本轮确实完成的动作才记为已验证。

向 QA 发出问题前，逐项确认：

- 已自行执行的排查及结果，尚有关键操作可执行时继续排查。
- 仍成立的具体假设，以及现有证据无法区分的现场观察。
- 该信息为何只能由 QA 提供，以及收到答复后执行哪项验证。

缺少字段本身不构成追问理由。工具或权限故障保存为维护侧阻塞，继续可独立进行的分析。必要分析无法执行时如实反馈进度，保留恢复条件。

## 选择问题

每轮选一到三个问题，按对当前判断的影响排序；每个问题必须通过上述完成条件。

| 缺口 | 处理方式 |
|---|---|
| 某项操作顺序、后续表现、复现条件、时间或原始材料决定下一项验证 | 询问 QA 能观察或回忆的具体事实；已有材料能确定时自行使用 |
| 原现场历史诊断仅由 QA 持有，且已有分析确认它能补齐影响判断的现场关联或事件观察 | 说明具体用途，请其通过「设置 → 诊断」导出覆盖故障时间的诊断；按 [Web 日志用途](web-logs.md#判断日志是否能补齐证据) 检查覆盖，不要求 QA 寻找内部日志字段；未记录的 DOM 状态另行验证 |
| 排查确认必须关联某台 Computer，但实际查询后仍有多个候选 | 按 [Computer 定位与 QA 询问](computer-target.md) 展示真实名称、平台或房间线索，请 QA 选择当时使用的设备 |
| 页面诊断确需现场本人允许访问 | 只说明用途和实际可见的授权操作；详细环境准备通过 [Web 接入引导](web-logs.md#发给用户的启用与授权引导) 在 setup 或明确求助时提供 |
| 浏览器桥缺失、CLI/MCP 未接通、认证或服务权限不足 | 维护侧记录具体失败、影响的验证、负责方和恢复条件；QA 只接收分析进度 |
| 证据已足以确认根因 | 完成报告与交接 |

维护方未知时标记待确认，写进「待核实与阻塞」供维护人处理；向其发送消息仍须有用户授权。现场资料缺口与技术阻塞分开写，只把 QA 能回答的问题发给 QA。

## 写给 QA

开工时可以简短确认「已收到，正在核对问题和相关证据」。分析后的正式回复以产品现象说明已确认的事实，初步判断注明未确认，再逐项写清必要的现场问题：

- **需要什么**：让 QA 确认一个看得见的表现、操作顺序或具体复现条件。
- **为什么需要**：用现场语言说明这个回答如何帮助缩小问题范围。
- **如何提供**：直接回复、选择实际设备名称，或提供必要的原始截图／录屏。需要导出现场诊断时说明产品中的可见入口。

QA 回复保持简短，包含真实记录链接与当前结论／进度。内部 Computer ID、taskId、文件路径、MCP、CLI、Token、AWS 权限及堆栈用于技术记录和维护对话；QA 只承担现场事实的补充。只有 QA 明确要求技术细节时，才解释相应内容。技术接入由维护方完成，页面授权需本人操作时使用上面的授权分支。

反馈、问题和来源追加到该 Bug 的「QA/RD沟通」字段（`feishu.py write --append dialogue=...`）。仍成立的假设与技术阻塞写进「排查验证」「待核实与阻塞」，供下次调用时从飞书读取恢复。

示例仅示意结构；前面的分析表述必须有本轮真实证据支持：

> 初步排查已把问题范围缩小到点击安装至出现授权页面之间，具体原因还需要确认。请补充：新开的标签页随后会跳转到 Slack 授权页面，还是一直空白？这能帮助判断问题发生在页面打开时，还是后续跳转时。直接回复即可。

> 已核对现有材料，但还无法判断是否只在切换设备后出现。请确认：不切换设备，重新执行相同步骤时也会出现吗？这用于判断设备切换是否是必要的复现条件。

证据充分时直接回填简洁根因并交接给方案阶段；只有技术阻塞时向 QA 说明「问题已记录，当前分析尚未完成，已保存现有资料」，维护侧保留详细恢复方法。上传了截图或完成代码阅读分别报告为对应进展，不能表述为根因已确认。

## 收到回复

用 `feishu.py read` 读取同一 `record_id` 的最新内容，把 QA 新补充的材料与上次提的问题逐项对应；之前的结论以飞书字段为准，用新证据重新验证。

回到问题分析 Skill 的第 1 步，更新代码基线并先自行执行已记录的验证，再反馈新结论或必要的下一轮追问。已回答的问题标记完成；仍需追问时重新满足追问前的完成条件。新材料推翻原根因时重新分析，并按工作流重新核实受影响的方案和批准。
