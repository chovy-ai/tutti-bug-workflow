# 现场材料与附件

每次提 Bug 固定采集两类现场日志：Web（页面日志）、Computer（召回包）；tutti-server 日志不在提 Bug 时拉，相关请求的 request id 记进排查线索，RD 排查时再查。全部原样作为 issue 评论附件上传，不脱敏。文件放在数据目录下的 `$REPORT`（`bug-reports/<operation_id>/`），上传后 Multica issue 与它的附件是唯一的事实来源。

## 采集结果状态

每类一个结果，记在会话上下文中，写进排查线索和最终回复：

| status | 含义 |
|---|---|
| `captured` | 取得并覆盖问题发生时间 |
| `empty` | 查询成功，结果为空 |
| `partial` | 取得一部分：截断、翻页中断或覆盖不足 |
| `pending` | 等用户提供：WebMCP 链接或诊断包、设备选择 |
| `blocked` | 无法采集，附原因（认证、权限、设备离线等） |

## 日志文件与附件

QA 的截图在建 issue 时挂上；其余现场在**一条**「现场材料」评论里用 `multica issue comment add --attachment` 一次发出，描述正文只写 Bug 表现（见 [issue 字段](issue-fields.md)）。

| 材料 | 上传什么 | 挂在哪 |
|---|---|---|
| QA 发来的截图、视频 | 原文件，先复制到 `$REPORT` | 建 issue 时 `--attachment`；issue 已存在时放进「现场材料」评论 |
| 排查线索 | `排查线索.txt`（见 [排查线索](issue-fields.md#排查线索附件)） | 「现场材料」评论 |
| Web 日志 | `merge_web_logs.py` 合并的 `web-logs.log`；或 QA 导出的 `tutti-web-diagnostics-*.zip` | 「现场材料」评论 |
| Computer | 召回包原件（`*.tar.gz`），不拆包 | 「现场材料」评论 |

规则：

- **一次发齐。** 等现场齐了再发「现场材料」评论；后到的文件发「现场补充」评论，只带新文件和更新后的 `排查线索.txt`，已经发过的不重复上传。
- **限制**：非空的普通文件；同一条评论里文件名不能重复（同名的先复制改名）；会在浏览器里执行的内容（HTML、SVG 等）先打成 zip。上传被拒（文件过大等）时优先去掉最大的召回包，在排查线索里写明本地路径，其余照发。
- **失败不发评论。** 任何一个附件上传失败，这条评论都不会发出：按报错修正后重发。结果不确定时先 `multica issue comment list` 回读，确实没发出再重发，不重复发评论。

不上传：查询的原始结果、解包后的目录、中间文件（它们留在 `$REPORT`，不删除）。缺失的来源写进排查线索的「日志核对」末尾和「现场材料」评论的采集状态，需要 QA 提供的写进描述「待 QA 确认」，并在最终回复里说明。
