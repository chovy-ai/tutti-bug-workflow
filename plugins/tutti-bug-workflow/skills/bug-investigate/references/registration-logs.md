# 日志采集与附件

提 Bug 时 Web 与 Computer 日志固定采集，Server 日志由 Agent 按分析需要决定（见 [服务端日志](server-logs.md)）。采集结果、文件和摘要都是本次会话的临时产物；上传后飞书记录是唯一的事实来源，不在本地保存采集清单。

## 采集结果状态

每个来源一个结果，记在会话上下文中，交给 `check_collection.py` 汇报现状：

| status | 含义 |
|---|---|
| `captured` | 取得与目标关联、覆盖所需时间的日志 |
| `empty` | 查询成功，结果为空；照常上传带 metadata 的文件 |
| `partial` | 取得一部分：截断、翻页中断、轮转或覆盖不足；照常上传并写明缺口 |
| `pending` | 等 QA 提供目标或材料，例如设备选择、连接链接 |
| `blocked` | 无法采集；写明原因，例如 `no_link`、设备离线、权限不足 |

采集失败不阻止后续分析。空结果、部分、失败分别如实记录，不把失败写成空结果，也不把没尝试写成失败。

## 日志文件与附件数量

上传到 Bug 表的「截图、视频、日志」（`field_map.attachments`），与 QA 的截图、视频放在一起，用 `scripts/feishu.py attach`（按文件名和大小跳过已在记录上的文件，上传后回读确认）。

| 取得形式 | 上传什么 |
|---|---|
| 已经是日志文件或包：QA 导出的 Web 诊断包、Computer 召回包 | 原样上传原件；包不拆开，不另传摘录 |
| 只读接口逐条返回内容（Server CLI、AWS 查询等） | 同一来源合并为一个 UTF-8 文件：`server-logs.log`；按事件发生时间升序，首行写 metadata（来源、查询参数、实际覆盖、截断），多行堆栈保持完整，只按同一事件 ID 去重 |

不上传：查询原始分页 JSON、工具发现结果、失败回执、DOM 中间结果、测试输出、分析草稿。截图和人工附件保留不动。Web 诊断包导出时已脱敏，原样上传。

## 采集情况

上传后用 `scripts/check_collection.py` 确认现状，把每个来源的结果写进「分析根因」的「证据」一节：来源、status、文件名、实际覆盖时间（含时区）、条数或大小、缺口或原因。只有截图、没有日志时如实写明，不称为已携带日志。
