# Task 字段与写入规则

提 Bug 用 `tutti-cli task create` 在当前 Room 建一个 Task，采集后用 `task edit` 改标题、写全描述并用 `--file` 挂上现场附件，`task assign` 指派跟进人。Task 只有下面几个可写字段，其余内容都写进描述。

| 参数 | Task 字段 | 怎么填 |
|---|---|---|
| `--operation-id` | Task ID／幂等键 | 第 1 步生成的 `operation_id`（UUID），重试时不变 |
| `--title` | 标题 | 一行「类别：现象（触发条件／关键对照）」，见下；`task edit --title` 可改 |
| `--description`／`--description-file` | 描述 | 建单时写 QA 原话；采集后 `task edit --description-file` 整段替换为下面的结构 |
| `task edit --file`（可重复） | 附件 | 截图、视频与全部日志，上传为 Task 私有附件、嵌在描述末尾；描述是整段替换，每次 `task edit` 都带上全部附件，见 [现场材料与附件](registration-logs.md) |
| `--priority` | 优先级 | 建单时按下表从 QA 定级映射；**CLI 改不了**，之后只能在任务看板改 |
| `task assign --user-id` | 负责人 | 跟进人的 Room 成员 userId（`tutti-cli user list --json`）；只更新负责人，不启动 Agent |
| `--project-id` | Project | 一般不填；QA 明确要求挂到当前 Room 的某个 Project 时才填 |

创建者是这台 Computer 当前登录的 Account；新建为 `todo`、未指派，不会自动启动 Agent。本 Skill 不改状态，不关闭、不删除 Task。分析根因、修复方案和验收不在本 Skill 写。

## 优先级

| QA 定级 | `--priority` |
|---|---|
| P00、P0（严重阻塞） | `urgent` |
| P1（明显 Bug） | `high` |
| P2（非核心 Bug） | `medium` |
| P3 | `low` |
| 拿不准 | `none`，描述「待 QA 确认」里写倾向和理由，QA 确认后在任务看板修改 |

QA 的原始定级同时写进描述的「分类」段，便于对照。

## 标题

RD 在任务看板里只看得到这一行，要让人不点开也知道「什么东西、在什么条件下、怎么坏了」：

- 格式：`类别：现象（触发条件／关键对照）`，40–80 字，一行。
- 现象写用户可见的结果和关键报错原文的要点，不写「异常」「有问题」这类空话。
- 括号里写区分条件：只在某种操作、设置、环境下出现，或与正常情况的关键差异。
- 只写事实，不写根因推测。
- **说清楚，不怕长。** 读的人没看过录屏、不知道内部概念，单看这一行也要明白：谁做了什么、看到了什么、哪里不对。用界面上的叫法和大白话（「右侧产出文件」而不是「产物」，「同一个文件」而不是「同一路径」）；不写只有排查过的人才懂的缩略说法，如「历史内容不同，未区分版本」。
- **「哪里不对」不明显时，把期望写进括号。** 比如显示了 3 条，读者不知道该显示 1 条还是 3 条都对，就写「期望只显示最新一份」。期望用 QA 的意思，不换成 Agent 根据数据推出的另一种期望。
- 采集中查到的、有助于理解问题的事实可以写进括号，但要换成读者看得懂的话（「三条内容各不相同，是三次修改的结果」），ID、哈希等细节放「现场核对」。

| 太简单 | 合适 |
|---|---|
| 任务：执行失败 | 任务：Claude Agent 执行任务报认证失败（模型 agnes-2.5-flash；同 Agent 同 Computer 普通会话 native/default 正常） |
| 房间：发消息失败 | 房间：本地房间 Codex 会话启动失败「cwd materialize failed」（仅本地房间，云端房间正常） |

| 意思没说清 | 合适 |
|---|---|
| 房间任务：同一路径文件更新后右侧显示3个同名产物（历史内容不同，未区分版本） | 房间任务：在任务里让 Agent 连续修改 guess_number.py 两次后，右侧产出文件出现 3 个同名 guess_number.py，看不出哪个是最新的（期望同一个文件只显示最新一份） |

建单时（第 2 步）还没有日志，先按用户描述写；采集完成后（第 4 步）如果确认了新的触发条件或对照，用 `task edit --title` 改成上面的样子。标题最长 512 字。

## 环境与版本（描述中的一段）

```
环境：PPE（lane-ppe-cloud-0928）
页面域名：ppe-cloud.tutti.sh
tutti-server：<service.version>
Computer：<computerVersion>（macOS arm64）
Web：<页面版本，可从页面日志或资源路径取得>
浏览器：<UA>
```

环境来自页面域名与 Server 日志的 namespace，两者不一致时都写上。

## 描述

纯文本，换行会保留，不渲染 Markdown；用空行分段，不用 `#`、`**`、表格。按下面的顺序写，**最重要的放最前面**：

```
概要
<2–4 句：什么坏了、在什么条件下、用户看到的报错原文、和正常情况的关键差异、影响范围>

现场核对（事实记录，不是根因结论）
- <对照>：失败的 <任务／会话 A> 用 <设置 X>；成功的 <会话 B> 用 <设置 Y>；两者 <相同的部分：同一 Agent、同一 Computer……>
- <日志事实>：<时间> <来源：Web／Server／Computer 日志> <报错原文或关键字段>（request id／task id）
- <请求失败>：<时间> <method 路径> → <状态码>（request id）；页面失败但没到服务端的请求单独列出

期望：……
实际：……
复现步骤：1. …… 2. ……
频率：必现／偶现（约 x 次中 y 次）
发生时间：2026-10-10 17:48（Asia/Shanghai）
操作账号：<名称>（<userId>）

关联 ID
账号：<userId>
房间：<roomId>
页面会话：<web-diagnostics:uuid>
Computer：<computerId>（<名称>）
Agent：<agentTargetId>
request id：<出错或关键的几条>
召回任务：<taskId>

分类
所属端：Mac／Windows／Web
业务模块：<功能名称>
QA 定级：P1（或「待 QA 确认」）
跟进人：<姓名>（已指派；未指派时写「待指定」）
上报人：<QA 姓名>

环境与版本
<见上一节>

页面链接：<出问题页面的完整 URL>

附件（已挂在本 Task）
- Web 日志：web-logs.log
- Server 日志：server-logs.log
- Computer 日志：<召回包文件名>
- 截图、录屏：<文件名>

待 QA 确认
- <还在等 QA 回复的问题；没有就省略本段>
```

规则：

- **期望、实际照 QA 的意思写。** 可以精简措辞，不改意思，不补 QA 没说的期望或备选方案（如「或者明确区分版本」）。QA 没说清期望时写「期望：待 QA 确认」，并在第 5 步问。
- **概要**第一句复述 QA 报的问题，再写现场核对得出的关键事实。查到的事实可能改变问题的含义时（例如 QA 说「同一份文件」，数据显示三条内容各不相同），两种说法都写、标明来源，在第 5 步请 QA 确认；不要用发现改写 QA 的问题，也不要把同一件事在标题、概要、期望里写成不一样的说法。
- **概要**和**现场核对**写给 RD 第一眼看。采集中核对过的每一条事实——成功／失败的对照、设置或版本差异、报错原文、服务端失败请求、日志里的异常——都写进「现场核对」，带上来源和时间，**不要塞进「关联 ID」**。
- **关联 ID** 只放 ID，不写说明文字。
- 在回复里告诉用户的每一条发现，都必须能在「概要」或「现场核对」里找到；回复里说「已建 Task」之前先用 `tutti-cli task show` 回读确认。
- 只记录核对过的事实，标注来源；推测写成「待确认：……」，不写根因结论（根因由 bug-solution 分析）。
- **不写过程记录和自我说明。** 采集窗口、条数、分页、去重方式、「本轮未重新提交／未刷新」「不能据此认定……」「HTTP 200 不能证明……」都不写；日志在附件里，过程在会话里。只有现场缺了一块且影响判断时，在「现场核对」末尾用一句话写缺什么。分类、环境与版本、附件各写一次，不在概要里重复。
- 没有的项省略，不要编造。
