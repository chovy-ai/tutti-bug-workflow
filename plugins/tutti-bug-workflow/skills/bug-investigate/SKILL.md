# QA Bug 上报与根因分析

你负责接收 QA 的问题、验证根因并保存可供 RD 继续分析的证据。普通 Bug 上报默认执行完整分析流程；只有用户明确要求本次仅登记或仅补附件、不做分析时，才在登记完成后结束。诊断用的临时测试或插桩只放在隔离工作区，记录用途和是否保留；正式方案协商与业务修复由后续场景负责。

「帮我记个 Bug」本身不等于「仅保存描述和截图」。即使用户明确只登记、不分析，也必须完成登记阶段的现场证据检查与可获取日志的保存；只有用户明确限制日志读取时才遵循该限制。涉及服务端链路的上报，按 [服务端日志](../../references/server-logs.md) 判断并立即执行采集：必需、建议补或可辅助均不能停在建议，优先复用实际 Tutti CLI，能力不足且来源已核实为 AWS 时使用 AWS CLI；已有权限内不等待 QA 再问。涉及 Web 的上报，先按 [登记阶段的 Web 采集判断](../../references/registration-logs.md#登记阶段的-web-采集判断) 检查已授权页面与原生日志能力，不能以「截图足以登记」「日志仅可辅助」或「尚未开始根因分析」跳过这一检查。

在本轮可自行完成的代码阅读、目标查询、证据采集与假设验证完成后，按 [QA 反馈、追问与恢复](../../references/qa-dialogue.md) 组织回复。QA 看到已确认的事实、当前判断与必要的现场问题；工具和权限细节保存到维护侧阻塞记录。

工具缺口按 [场景工具 Setup](../../references/tool-setup.md) 使用 `investigate` 清单，只启用问题链路需要的日志/复现工具。工具准备由维护侧处理，继续本轮可独立完成的分析。

## 1. 接收最新问题

读取 [工作流与交接](../../references/workflow.md) 和数据目录配置。新 Bug 先登记，按 [登记时自动采集与附加日志](../../references/registration-logs.md) 分别判断 Web、Computer、Server，先保存易失证据和可获取的相关日志；已有 Bug 沿用同一记录。缺少某类日志或现场字段时保存待核对项，继续可独立执行的分析。

已有 `record_id` 时按 [飞书适配](../../references/configuration.md#飞书命令适配) 读取同一条 Bug 的最新字段、附件和 QA 回复。已有档案继续使用；缺少档案时运行 `scripts/workbench.py new-bug --bug-id ID`。缺少基础配置时进入 `$tutti-bug-workflow:bug-setup` 排查，待补配置保存到维护侧记录。

整理期望行为、实际行为、复现步骤与频率、发生环境、时间与时区、目标标识和现场版本。实际查看可访问的截图／录屏，记录来源；未读取的附件标记待读取。把 QA 描述、Agent 已验证的事实和待验证的推断分别记录。

登记时分别判断 Web、Computer 与 Server 日志的必要性，记录用途与依据，按 [登记日志规则](../../references/registration-logs.md) 选择采集范围。需要 Computer 日志时，按 [Computer 定位与 QA 询问](../../references/computer-target.md) 从已有证据与实际目录查询关联目标。仍有多个候选时暂缓该目标的日志读取，把必要的设备选择留到第 5 步；先继续其他可用证据与代码分析。

完成条件：已唯一定位或成功创建记录，保存本轮输入、来源引用、日志结果与待核对项，并满足 [登记日志完成条件](../../references/registration-logs.md#4-写入同一条-bug)。无法唯一定位记录时保存本地材料，暂停回填并继续可进行的分析。普通上报进入第 2 步；明确仅登记或仅补附件、不分析时，仍须完成上述登记证据步骤，成功后进入第 7 步确认本次提 Bug 范围已结束，再反馈真实登记结果。

## 2. 固定代码基线

每次开始分析或收到 QA 补充后恢复分析，按 [固定代码缓存](../../references/repository-cache.md) 增量同步 `tutti`、`tutti-server` 的最新远端 main。使用本轮成功返回的 SHA、快照和缓存路径，为两个仓库准备独立 worktree；分支使用 `codex/<bug-summary>-analysis-<run-id>`，保留已有工作区及改动，读取适用的 `AGENTS.md`。

在 `bug.json.baselines` 保存两仓库 SHA，在报告保存获取时间和工作区。QA 现场版本另行记录；main 和现场的差异作为待验证条件。一次运行固定使用本轮 SHA，恢复时评估新基线是否改变已有判断。

完成条件：两个最新远端 main 均已成功获取、固定并可读取。获取失败时保存已有材料、已完成的分析和维护侧恢复条件，以 `blocked` 结束本轮；QA 收到简洁的分析状态，技术故障由维护方处理。

## 3. 建立问题链路和假设

从复现入口阅读相关代码与测试，在 `analysis.md` 画出参与模块的请求／数据／状态流，标注关键边界的期望行为、实际观察和待验证位置。覆盖实际参与的 Web、服务端与 Computer；认定某端不参与时写明依据。

按 [业务逻辑、日志与复现路径](../../references/root-cause-analysis.md) 建立正常业务路径，逐节点对齐同次操作的日志上下文，解释触发条件如何经过首个错误状态、后续消费与恢复分支形成 QA 的最终现象。列出候选原因及各自的证实／排除条件，把版本差异、材料冲突和恢复后的成功事件纳入假设。

完成条件：业务状态与日志可逐节点关联，每个候选都有可观察的证实／排除条件；未闭合的因果节点已明确对应下一项采集或验证。

## 4. 获取证据并验证

先复用本条 Bug 的 [登记日志清单](../../references/registration-logs.md#保存证据与采集结果)，检查目标、范围和完整性；新材料或覆盖不足时补采，按 [集中附件规则](../../references/registration-logs.md#日志文件与附件数量) 保存和上传。先自行获取已有权限内的证据，再决定需要 QA 补充什么。只读取与本条 Bug 的目标、环境和时间相关的来源；根据分支加载对应文档：

| 分支 | 必读参考 |
|---|---|
| Web 页面日志、截图身份识别；发现或授权失败 | [WebMCP 日志与页面识别](../../references/web-logs.md)，含启用截图和历史诊断导出方式 |
| 本地 Computer | [Computer 日志获取](../../references/computer-logs.md#本地读取指定文件)，按明确文件路径核对目标和覆盖范围 |
| 远端 Computer | [Computer 日志获取](../../references/computer-logs.md#远端复用-tutti-日志召回) 和 [tutti-ops CLI](../../references/tutti-ops-computer-logs.md)，完成召回、下载、校验和读取 |
| 服务端请求／成员／权限／持久化／投影日志 | [服务端日志](../../references/server-logs.md)：判断必需／建议补／可辅助后本轮立即调用实际 Tutti CLI；入口覆盖不足且已确认AWS来源时调用 [AWS CLI](../../references/aws-cli.md)，保存并附到同一条Bug |

### 判断与自动采集 Server 日志（必须执行）

每轮记录 Server 参与边界、`required/supplementary/not_needed/undetermined`、缺失观察与已有替代证据。`required`或`supplementary`包含“建议补／可辅助”，都按 [服务端日志](../../references/server-logs.md) 在本轮立即查询、保存、上传并回读，不以建议结束或等待用户追问。先取得易失证据再深入分析；成功请求不能以仅覆盖失败的Tutti查询代替。采集受阻时立即尝试已有授权的适用替代入口或登录恢复，保存具体阻塞和恢复条件；无需追加须有充分证据。

### 判断是否补充 Web 日志（必须执行）

涉及 Web 的问题，在复用登记材料后明确记录「需要补充／可辅助／无需追加」、对应假设、缺失观察和取得证据后的验证动作。按实际日志契约核对能否提供所需信息，不能仅因缺少日志而要求 QA 补材料，也不能因 main 最小复现成功而跳过现场关联。

**判断「需要补充」后，本轮必须自动执行采集，不能以「需要 Web 日志」结束或等待 QA 再次询问。** 将 Bug 排查请求视为在已有访问权限内读取相关页面日志及必要可见 DOM 的任务授权；复用会话中已有授权，无需再问「要不要获取 Web 日志」。结合用户截图先匹配原现场，再发现并调用 WebMCP，检查实际覆盖、验证假设、保存证据并回填同一条 Bug。具体执行与完成条件见 [截图与 WebMCP 自动采集](../../references/web-logs.md#截图与-webmcp-自动采集必须执行)。只有实际缺少新增访问权限、无法唯一定位目标或原现场仅由 QA 持有且决定下一项验证时，才请求必要信息或实际授权；继续不依赖该缺口的排查。

| 当前证据缺口 | 补充与验证动作 |
|---|---|
| 代码已复现，但原现场页面、加载版本或触发链路未关联，且差异影响根因判断 | 优先获取与原页面和故障时间对应的历史诊断，核对实际记录中的身份、版本及事件；缺失字段继续保留待核实，不把当前公开部署包或新页面日志当作旧现场 |
| 候选原因涉及异步时序、请求失败、重试或状态切换，已有材料无法区分 | 获取对应范围的日志，用实际事件证实或排除候选；避免收集无关全量日志 |
| 定位、焦点或交互问题需要点击元素、mention URL、activeElement、DOMRect、实际锚点及激活到开窗的时序 | Web 日志可辅助关联现场；先检查是否记录这些状态。未记录时补现场最小复现、断点或必要的临时观测，按已有授权与隔离诊断规则执行，不新增生产埋点；网络错误日志不足以证明 DOM 定位因果 |
| 现有证据已关联现场并足以区分影响结论的候选原因 | 无需追加日志，不将日志数量或某一种日志来源设为确认根因的固定门槛 |

有可访问来源时自行采集；只有 QA 能提供的原现场诊断确实决定下一项验证时，按 [QA 反馈规则](../../references/qa-dialogue.md) 说明需要什么、为什么及产品导出入口。浏览器桥或权限等技术缺口保存到维护侧，继续独立分析。日志成功取得、为空或缺少关键状态都不自动代表现场根因已确认；详细处理见 [Web 日志的证据用途](../../references/web-logs.md#判断日志是否能补齐证据)。

### 使用 WebMCP 的执行规则（必须执行）

用户粘贴 WebMCP 连接链接或 `web-diagnostics:…` ID 时，优先自动调用插件 `tutti-diagnostics.collect_web_logs`，固定原提问前 10 分钟并保存 `web-logs.log`，然后上传和回读附件。插件通过官方 Chrome MCP 调用本机页面原生 WebMCP，不使用 Browser Use 或 UI 自动化；Chrome 需要启用 WebMCP 并允许远程调试连接。新版页面日志无需脱敏。具体见 [本机 Chrome WebMCP](../../references/web-logs.md#首选本机-chrome-webmcp)。

1. **先匹配现场**：核对截图、Account、房间／会话、故障时间与标签页；有水印时匹配工具描述及结果中的页面 ID。没有水印时保存其他关联依据及限制，不把相同 URL 当作同一页面。
2. **先发现能力再判阻塞**：读取当前宿主工具文档，检查已授权浏览器的页面发现、原生工具发现及执行能力。`browser_bridge` 空配置或 `doctor` 提示未配置，不能直接证明当前会话不能访问；宿主支持时可按 [已验证的 CDP 路径](../../references/web-logs.md#宿主浏览器能力发现与-cdp-路径) 调用。遵守本轮浏览器操作授权和适用 AGENTS.md，不绕过权限或伪造用户手势。
3. **执行固定窗口采集**：读取实际 `get_web_logs` 描述、schema 与只读标记，保存提出本次问题的时间及来源，固定提问前 10 分钟。省略 level、设置 limit 200，查询能覆盖固定窗口的最小受支持范围，再截取目标页面／Account 的全部保留记录；不能用采集时间取代提问时间，也不能仅筛关键事件。按 [固定流程](../../references/web-logs.md#固定流程提问前-10-分钟--单个-log-附件) 处理延迟、截断、聚合边界和历史缺口；额外假设查询另记用途。
4. **检查实际覆盖**：逐次保存参数、页面 ID、查询起止、记录实际时间、重复次数与 `truncated`；结果截断时不能把请求的 12h 写成已取得完整 12h。分级查询分别判断完整性，warn/error 完整不能补齐遗漏的 info，无分页的接口不能虚构翻页。
5. **补齐因果观察**：日志用于确认同次操作的入口和时序；定位问题另取获授权的可见 DOM、触发元素属性／矩形及实际锚点。观察时的 activeElement 不等于点击或开窗时的焦点；同时出现的网络错误不等于位置错误根因。Computer 日志按下一节评估。
6. **保存日志并自动上传**：逐条取得的记录按时间归并为 `web-logs.log`；已有诊断文件或包按 [集中附件规则](../../references/registration-logs.md#日志文件与附件数量) 保留原样上传。保存 SHA-256／file token 并回读，记录实际覆盖、空结果、失败和限制。截图、工具发现、查询回执与必要 DOM 保存在本地证据，不逐项上传过程文件；详细采集规则见 [Web 日志获取](../../references/web-logs.md)。

### 判断是否需要 Computer 日志（必须执行）

每轮明确判断 Computer 是否参与故障链路，以及它的日志是否能补齐当前缺失的因果证据，记录「必需／补充／无需采集／待判断」、候选原因、目标、期望观察及取得材料后的验证动作。日志必要性与采集状态分别保存；材料不足或工具不可用不能标记为不适用。

| 当前证据与候选原因 | 采集判断与验证动作 |
|---|---|
| 首个异常或待验证边界涉及 Computer 上的安装、配置／授权执行、Agent／工具／命令执行、文件访问、连接、状态同步、进程或 VM 生命周期，现有证据不能区分原因 | 必需：确认故障时的 Computer 与环境，按时间、请求／任务／会话及版本取得能验证该边界的日志；根据实际写入链路选择 desktopd、Companion、runtime-host 或相关执行诊断，不固定收集所有组件 |
| Web 已解释表面现象，但 Computer 执行结果、返回时序或状态差异仍可能改变根因判断 | 补充：关联同一次操作的 Web 与 Computer 证据，核对发出、执行、结果与投影的先后关系 |
| 代码与现场证据支持错误发生在纯 Web 渲染、焦点或锚点选择，Computer 结果不影响该错误；或已有现场证据足以区分相关候选 | 无需采集：写明因果边界或已有替代证据。仅确认该来源不参与问题时标记 not_applicable；相关但已有证据充分时记录无需追加，不强制召回 |
| 是否参与、故障目标或对应操作尚不明确 | 待判断：继续代码与可用现场证据分析；确需目标后再查询候选。不能仅凭「连接器」「授权」字样认定需要 Computer 日志，也不能凭本地 UI 复现排除现场跨端因素 |

已有日志或召回包足够时复用，只补缺失范围。当前选中设备、执行 Agent 的本机及其他设备的日志不能替代故障目标；权限不足、设备离线、路径不可读、包未下载或覆盖不足分别记录并按维护侧恢复。只有影响下一项验证且 QA 能回答的设备或操作事实才提问。日志取得或没有 error 均不证明根因；检查必要状态事件与实际覆盖。详见 [Computer 日志用途](../../references/computer-target.md#1-判断日志用途)。

每取得证据后，按 [因果推演与补采](../../references/root-cause-analysis.md#2-用缺失的因果节点驱动补采) 重算业务路径；无法推出最终现象或与日志冲突时修订假设，沿缺失节点继续获取 Web、Server、Computer 或必要的响应／状态上下文。结合真实 owner 的测试、断点或最小复现验证主路径，再检查同一错误状态的其他可达路径，分别保存推演、实际执行结果与证据位置。

完成条件：主复现路径已推演并按可用条件验证，其他相关路径已检查；每个因果节点都有证据或具体缺口／下一动作。解释中间报错或取得某类日志不能替代对最终业务现象的验证。还有可自行执行的关键验证时继续；某个来源不可用时继续验证其他边界。

## 5. 判断根因或提出追问

标记「已确认」须同时满足：

- 已定位触发条件与第一个错误状态，代码路径能解释它如何传播成 QA 观察到的现象。
- 按 [根因完成条件](../../references/root-cause-analysis.md#5-确认根因的完成条件) 闭合业务逻辑与日志因果链，主复现路径解释原现象，其他可达路径已检查并区分实际复现与推演。
- 实际日志、测试或复现结果验证了关键因果关系，证据能关联本条 Bug 的目标和现场。现场版本未知时，明确它是否影响结论；影响时先补证。
- 影响结论的竞争假设已有验证结果，材料冲突和反例已得到解释。

未满足时标记「原因未确认」，保存已知事实、仍成立的假设和最关键的缺口。先核对第 1–4 步的实际结果；尚有可自行取得的关键证据或可执行的验证时返回第 4 步。只有 QA 能提供、且回答会改变下一项验证的现场信息，才按 [QA 反馈、追问与恢复](../../references/qa-dialogue.md) 提问；阻止必要验证的工具接入、权限或环境故障单独保存维护侧阻塞与恢复条件。

完成条件：本轮可自行执行的关键排查已有结果；已形成有证据的结论，或每个 QA 问题均关联具体假设、已有验证、缺失观察及答复后的验证动作。只有维护侧阻塞时向 QA 反馈真实进度，保存技术恢复条件。

## 6. 保存并回填

按 [根因报告模板](../../assets/analysis.md) 保存 `analysis.md`，依据工作流更新输入、根因版本和对话记录。详细过程留在档案，飞书使用模板的简洁摘要及关键证据引用。

### 独立字段回填规则（必须执行）

以下规则直接适用于本 Skill。使用数据目录配置的 `feishu.field_map` 定位真实字段；不得将下面各类信息笼统拼入「根因分析」。

| 内容 | 飞书字段 | field_map 键 | 本场景写入范围 |
|---|---|---|---|
| 已确认事实、初步判断及确认程度 | 分析结论 | `analysis_conclusion` | 区分代码复现和现场根因确认 |
| 触发条件、首个错误状态、传播路径与影响 | 根因分析 | `analysis_report` | 两到四句说明因果链，保留必要证据引用 |
| 日志、假设验证、测试、主复现及其他路径、命令和实际结果 | 排查验证 | `investigation_evidence` | 区分路径推演与实际完成的修复前排查 |
| 各仓库 SHA、获取时间、工作区与现场版本差异 | 代码基线 | `code_baselines` | 保存本轮固定版本，保留其他运行记录 |
| 支持判断的文件、行号、仓库与版本 | 相关代码 | `code_references` | 精简关键路径，完整过程保存在本地档案并引用集中日志 |
| 根本方案与兼容方案的初步建议 | 修复方案 | `solution_report` | 仅在有建议时写入，明确「候选、未评审、未批准」，不覆盖已有 RD 方案 |
| 正式验收用例与通过标准 | 验收标准 | `acceptance_report` | 由 solution 场景维护，本场景保留 |
| 修复后的实际检查、部署版本与结果 | 验证结果 | `verification_report` | 由 execute 场景维护；首次登记可注明未执行，不覆盖已有结果 |
| QA 澄清、现场追问与原始来源 | QA/RD沟通 | `dialogue` | 追加本轮沟通，保留人工和 RD 内容 |
| 未验证假设、现场缺口、技术阻塞与恢复条件 | 待核实与阻塞 | `open_items` | 分开记录 QA 待答与维护侧条件，更新自己拥有的条目 |

修复前测试通过不等于修复后验证通过，代码最小复现不等于现场根因已确认。完整 `analysis.md` 保存到本地档案，字段回填业务因果链、主复现路径与其他路径的简洁结论；附件按 [集中附件规则](../../references/registration-logs.md#日志文件与附件数量) 提交，不逐轮上传报告或过程文件。

写入前读取最新记录，只修改本场景拥有的字段或条目，保留人工内容、其他场景结果及原附件。发现旧「原因分析」内仍有混合分节时，先保存原始内容，只在用户授权范围内迁移到独立字段；不得批量覆盖历史 Bug。字段缺失时读取实际表结构并补齐配置映射，无法完成时保存具体回填缺口，不得退回单字段汇总。详细迁移规则见 [报告字段契约](../../references/report-fields.md)。

回填前重新读取记录：问题字段、附件或 QA 回复变化时回到第 1 步；仅报告被编辑时合并最新内容。按 [独立字段回填契约](../../references/report-fields.md) 分别更新分析结论、根因分析、排查验证、代码基线、相关代码和待核实项，向 QA/RD沟通追加 QA 问题与来源。根因字段只写简洁因果链；候选建议可写修复方案并明确未评审，已有方案、修复后验证和人工内容必须保留。不得把基线、路径、方案及沟通重新汇总进根因字段。按实际工具结果确认写入情况，再按首个满足的条件记录状态：

| 本轮结果 | 档案状态与交接 |
|---|---|
| 根因已确认，报告保存且回填成功 | `pending_solution`，交接根因、证据、代码基线与剩余限制 |
| 必要现场资料已向 QA 提问并回填成功 | `waiting_qa`，保存待答问题及收到回复后的验证动作 |
| 必要验证仍受维护侧条件阻塞，或回填失败 | `blocked`，保存已完成的分析、未完成项和维护侧恢复条件 |

飞书阶段保持「bug单」，后续推进遵循工作流。维护侧阻塞与 QA 待答问题分别保存；QA 答复能推进下一项验证时使用 `waiting_qa`，其余技术缺口保留在报告。结束时按 QA 反馈规则说明实际结论或进度，区分已确认与初步判断；等待 QA 时结束本轮，回复到达或用户再次调用后从第 1 步恢复。

## 7. 确认提 Bug 结束并上传会话

这是提 Bug 流程的独立收尾节点，按 [结束判断与 session 上传](../../references/session-upload.md) 执行：确认结束 → 固定当前会话快照 → 按当前 provider 上传 → 核对并保存回执 → 最终反馈。

1. **确认结束**：按用户已授权的本次范围核对完成条件。默认完整分析须根因已确认、报告和证据已保存、必要字段成功回填并回读，已进入 `pending_solution`；明确只登记或只补附件时，须该范围内的登记、证据保存和回填均成功。记录结束依据与对应输入/运行版本，不为这个已授权的收尾节点重复索要确认。用户明确结束本次提 Bug 范围时，保存未完成项与原始指令后也可收尾，保留真实根因确认程度。
2. **暂未结束**：仍在采集或分析、等待 QA 答复、必要验证暂时受阻、回填失败时，保存进度和恢复条件，按 QA 反馈规则结束本轮回复；这些情况不触发上传。下一次补充或恢复后重新判断，不把每次回复、状态保存或收到新日志当作结束。
3. **上传与反馈**：确定结束后、最终反馈前，按引用核对当前宿主 provider 与本会话身份，固定并脱敏原生 JSONL 快照，上传到 Tutti 管理端并保存确认回执。相同结束节点重试复用稳定快照，已成功则复用回执。上传受阻独立记录归档状态和恢复条件，不改写已完成的业务结果。最终反馈说明实际上传结果。

完成条件：本次提 Bug 的结束依据已保存，session 已确认上传并保存回执，或已保存真实归档失败与恢复条件。尚未结束时本节点保持待执行；后续方案、修复验证、纯 Setup 或 Skill 维护不自动触发本节点。
