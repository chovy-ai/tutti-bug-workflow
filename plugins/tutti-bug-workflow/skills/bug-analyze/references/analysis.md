# 分析要求与回复格式

拉好代码（SKILL 第 2 步）后，按下面的要求分析，回复按「回复格式」写成 Markdown，作为 issue 评论发出。

## 怎么做

1. 分析根因。从现场出发：按发生时间和关联 ID 在日志里找到出错的那几条，排出时间线，再在代码里找到对应实现，解释为什么会这样。因果链每一环都要有日志或代码作证，没证据的标成假设；现场不够就写进「待确认」，照常给出结论，不要提问等待。

2. 先弄清模块设计，再出方案。动手设计方案前，先把这个功能所在模块的整体设计弄清楚：涉及哪些端和组件、各自负责什么、数据和状态怎么流转、现有的约定和抽象是什么、同类问题在模块里别处是怎么处理的。方案要顺着这套设计来，复用已有的机制和约定，不另起一套，不在调用点打补丁绕过；如果问题恰恰出在设计本身，直接指出来，并说明顺着现有设计修和调整设计各自的代价。
   给出两个方案并比较：
   - 根本方案：从根上消除原因；
   - 兼容方案：改动更小、风险更低的做法。
   比较覆盖范围、对模块设计的影响、兼容性、改动成本、回归风险和回滚方式，最后给出推荐。两个方案相同时说明原因。

3. 画修复前后的工作流程图。用 Mermaid sequenceDiagram 画两张，按端分泳道（用户／Web 前端／Server／WebSocket／Computer／数据库，用到哪个画哪个）：
   - 修复前：现在的实际流程，出错的那一段用 rect rgb(253, 226, 225) 包起来，Note 写「❌ 根因：……」；
   - 修复后：推荐方案落地后的流程，改动的那一段用 rect rgb(230, 244, 234) 包起来，Note 写「✅ 修复：……」。
   两张图的参与方和前后步骤对得上，只有改动的部分不同。文字用大白话，不写类名、函数名、错误码常量；每张不超过 10 步，每个框和箭头不超过 20 个字；一端内部的动作用 Note，不画自己指向自己的箭头。

## 回复格式

Markdown，按下面的顺序写；开头三段让人只看它们就明白发生了什么。流程图用 ```mermaid 代码块。

```markdown
## 根因
两三句大白话，150 字以内：哪个环节、在什么条件下、做错了什么，导致用户看到什么。不堆术语、不贴 ID。

## 复现路径
前置条件和操作步骤，到出现问题的那一步。

## 预期工作流程
正常应该怎么走（每一步由哪一端做什么），并指出实际在第几步偏离。

## 模块现状
这个功能涉及的组件和职责、数据／状态流转、相关的现有约定（几行即可）。

## 修复方案
根本方案与兼容方案（做法、改动、兼容性与风险、回滚）、取舍、**推荐方案**及理由。

## 修改范围
按仓库列出要改的文件或模块和实现要点，以及要补的测试。

## 修复前流程图
## 修复后流程图

## 验收要点
修复前怎么复现；修复后要验证的用例（原问题、边界、回归），逐条编号，修复 Agent 按它自验证。

## 证据
时间线、日志（附件名、时间、request id、关键内容）、代码位置（仓库@sha 路径:行号）。

## 影响范围
哪些端、场景、用户会遇到；是否影响数据。

## 待确认
还没证实的假设，以及怎么验证。

分析依据：tutti@<sha>，tutti-server@<sha>，tsh-websocket@<sha>（没看的仓库不写）

请 RD 评审：认可就在评论里写明采用哪个方案，再把 issue 分配给修复 Agent；有问题直接评论，我会在这里补充。
```
